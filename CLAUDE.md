# React-WP

A WordPress-style CMS: React 19 + Vite SPA, Supabase (Postgres + Auth) as the whole backend, and a small Node server (`server.mjs`) for self-hosting. README.md explains each feature and why it was built that way — read it before changing anything.

## Commands

- `npm start` — build, then run `server.mjs` on :3000. This is how the site is actually hosted.
- `npm run dev` — Vite on :5173. It starts `server.mjs` on :3000 itself (`vite.devApi.mjs`) and proxies `/api` there, so one terminal is enough and Step 3 of the Setup Wizard works exactly as it does on :3000. If port 3000 already answers (someone ran `npm start`) that server is reused instead of spawning a second one; `RWP_DEV_API=off` skips starting one at all. Vite answers an unreachable API target with an empty `502`, which is what used to surface as `Connection test failed (HTTP 502)`; the proxy now writes a JSON body naming the real problem.
- `npm run build` — the SPA build, then `npm run build:api`, which bundles `src/server/**` — plus `supabase/schema.sql`, inlined as `__RWP_SCHEMA_SQL__` — into the git-ignored `src/server-dist/vercel.mjs` that `api/index.ts` and `api/install-schema.ts` both import. The Vercel function **must** be that bundle: Vercel transpiles each file under `api/` on its own and keeps relative specifiers extensionless, and these functions run under Node's native ESM resolver (`"type": "module"`), so importing `src/server/adapters/vercel.ts` — or anything a `.ts` file re-exports — fails with `FUNCTION_INVOCATION_FAILED` on every request. For the same reason nothing under `api/` may read a repository file at runtime or use `__dirname` (it does not exist in an ES module): `api/install-schema.ts` used to read `supabase/schema.sql` from disk and answered Step 5 of the Setup Wizard with `Database setup failed: __dirname is not defined` on every install.
- `npm run lint` and `npm run typecheck` (`tsc --noEmit`). ESLint only covers `.js/.jsx`, so `.ts/.tsx` files are not linted.
- `git` is not on the shell PATH. Use `C:\Users\arash\AppData\Local\GitHubDesktop\app-3.6.5\resources\app\git\cmd\git.exe`.

## Database schema

`supabase/schema.sql` is the whole database schema and is **run by hand in the Supabase SQL Editor**; the app cannot change its own database. There is no `supabase/migrations/` folder: the schema lives in this one file, and it only ever creates what is missing, so re-running it on an existing database adds whatever it lacks and never loses data.

There are **two kinds of fresh-install schema**:

- `supabase/schema.sql` — **core CMS only** (23 tables: pages, posts, categories, comments, profiles, profile_details, options, menus, media, media_folders, plugins, theme_settings, rwp_quota_overrides, rwp_role_capabilities, rwp_user_capabilities, rwp_translations, likes, follows, taxonomy_follows, bookmarks, page_views, rwp_view_salts, rwp_security_secrets). Run by `server.mjs` and by `POST /api/install-schema` (`src/server/index.ts`) during the Setup Wizard. `server.mjs` reads the file; the bundled serverless copy carries the same text inline (`vite.api.config.mjs` → `__RWP_SCHEMA_SQL__`), because a Vercel function's filesystem holds no repository.
- `plugins/<id>/schema.sql` — everything that plugin owns, declared in its `manifest.json` `database` block. Run **on activation** by `POST /api/admin/plugins/install-schema`, so a site that never enables the shop never gets its twenty `shop_*` tables.

A plugin's `schema.sql` may depend on core (`user_has_cap`, `pages`, `profiles`, `options`) but **core must never reference a plugin object**, and one plugin must never reference another's. `pages.builder_data`, `.builder_data_i18n`, `.is_builder_enabled`, `.is_site_template` and `.template_type` are **core columns** despite being builder-shaped: core's `rwp_install_default_content` and `builder_create_site_template` write them, and `<SiteTemplate>` renders the header/footer from them without the builder installed.

Each plugin also ships `uninstall.sql`, run only when an administrator explicitly asks to wipe its data. It drops only what that plugin's `schema.sql` creates, and says in a comment what it deliberately keeps.

Every schema file must be safely re-runnable, because partial failures get re-run:

- `drop policy if exists` for the **new** policy name, not only the one being replaced, before every `create policy`.
- `drop trigger if exists` before every `create trigger` (Postgres has no `if not exists` for triggers).
- `if not exists` on tables, columns and indexes.
- End with `notify pgrst, 'reload schema';` or PostgREST won't see new columns.

Audit that programmatically before handing a schema file over. Getting this wrong has broken reruns twice.

The split can be exercised end to end in PGlite: run `supabase/schema.sql` alone, assert no `shop_*` / `elementor_templates` / `code_snippets` table exists, then each `plugins/<id>/schema.sql`, then each `uninstall.sql`, then assert the 23 core tables are still there and every plugin reinstalls.

A plugin's `schema.sql` is the only copy of its objects: nothing is duplicated into core, and with `supabase/migrations/` gone there is no second file to keep in step. `plugins/rwp-shop/schema.sql` owns `shop_settings()` and `shop_calculate()`; the page builder's own `schema.sql` owns `elementor_templates` and the builder functions; `plugins/rwp-chat/schema.sql` owns the chat tables.

## Things that are not obvious from the code

- **Roles live in `public.profiles`, not `user_metadata`** (users can rewrite their own metadata). The capability map is duplicated: `src/lib/roles.ts` drives the UI, `public.user_has_cap()` drives RLS. Change both or neither.
- **Capability grants (Settings → Roles) are two tables**, `rwp_role_capabilities` and `rwp_user_capabilities`, read by `user_has_cap()` and loaded into `roles.ts` by `loadCapabilityGrants` (`src/lib/capabilityGrants.ts`) before the first render. `hasCapability(role, cap)` adds the signed-in person's own grants only when `role` is theirs; to show someone else's, combine `capabilitiesFor` with their rows. Writes are allowed for `profiles.role` administrator/super_admin only, **never a capability**, or granting `manage_options` would let a role grant itself everything. In `user_has_cap` use `$1`, not `capability`: inside the subqueries that name is the column. The old four toggles in `rwp_app_settings.roles` were migrated out and the key removed.
- **Account pages have fixed paths** (`/login`, `/register`, `/lost-password`, `/profile`, `/dashboard`; `src/lib/account.ts`). `App.tsx` resolves each to the built-in screen, a page (`<PublicContent pageId fallback>`, so a missing page falls back instead of locking people out) or a custom URL, from the `<key>_page_id` / `<key>_page_url` options. Always link to the fixed path, never a page slug. Sign-out goes through `signOutAndRedirect` (honours `logout_redirect`); sign-in destinations through `afterLoginUrl`, which only accepts same-site `?redirect=` paths. The forms are shortcodes (`[rwp_login_form]` …, `src/lib/builtin-shortcodes.tsx`). The public toolbar is gated by the `admin_toolbar` option in `PublicLayout`.
- **Default content is core's** (`src/lib/defaultContent.ts`, from `InstalledDashboard` for `manage_options`): group 'site' (Home as front page, Blog, Sample Page/Post, policies) runs only on a site without pages, and must run before 'account' (the account pages are pages). Plugins change items via the `rwp_default_content` filter; the builder adds layouts and site templates there instead of installing 'site' itself. Items set options only through the whitelist in `rwp_install_default_content`.
- **Floating Login is core, not a plugin** (Settings → Floating Login; `src/lib/floatingLogin.ts`, `src/components/floatingLogin/`, rendered by `PublicLayout`). Its settings are six `floating_login_*` option rows seeded by `schema.sql`. The Register tab also requires `users_can_register`. The button is z-index 9850 (above the header, so top corners work), the dialog 9985; keep the `rwp-fl-*` classes global for Custom CSS.
- **New accounts get their role from the `default_user_role` option**, applied by the `handle_new_user` trigger. Never read a role from the signup payload. Administrator and super_admin are refused on purpose.
- **An RLS-blocked UPDATE returns no error and affects zero rows.** Use `.select()` and check the returned rows before reporting success. The SQL adapters are the mirror image: `update`/`delete` hand rows back only when the filter carries `columns` (`{ where, columns: 'id,role' }`), otherwise they answer with an empty array — the same "did it land?" question, so check the row you asked for, not the array's length.
- **`saveSettings` in an install request decides exactly one thing: whether `data/react-wp-config.json` is written.** The database work — schema, the `site_title`/`admin_email`/`installed` options and the administrator's promotion — is unconditional in both installers, and both answer `{ mode, installed, env, admin }`. In `server.mjs` it used to gate the whole block, so a wizard run in serverless mode applied the schema and skipped the promotion: the new administrator kept the `subscriber` row `handle_new_user` gives every sign-up, and the bare `{ success: true }` left Step 5 with no credentials to show. `env` now comes back for persistent answers too (the config file is what that host reads, but the same block is what a Docker/Vercel copy of the site needs), and `admin` is the role the `profiles` row was *read back* with — never an assumption, so a promotion that matched no account is a warning in the wizard. `server/installEnv.mjs` mirrors `buildEnvString` in `src/server/index.ts`; change both or neither.
- **A wizard re-run must be safe.** The Supabase path tolerates an existing account (`signUp` returns "already registered"), the universal engine refuses it, so `POST /api/install-schema` looks the account up and promotes it instead of answering 500 — a re-run is how a site whose administrator ended up with the wrong role gets put right. The same reason `install()` in `server.mjs` resolves the Supabase project reference from the request body's `supabaseUrl` (as `/api/install/test-db` already did): a fresh install has no `data/react-wp-config.json` to read a reference out of, and Step 3 passing while Step 5 fails is the least useful pair of answers.
- **`server/autoSetup.mjs` is the boot-time half of installation, and it exists because the two sides of the site disagreed about what "configured" means.** The browser reads `VITE_SUPABASE_*` from `.env.local`; `server.mjs` read only `data/react-wp-config.json`, so a site whose schema and `options.installed = 'true'` row were already in the database still answered *"This site is not installed, so plugins cannot be uploaded"* — the server believed it was unconfigured, and every admin route guarded by that message refused. The module's rule is **configured ⇒ installed**: `resolveSiteConfig()` (what `readConfig()` in `server.mjs` now is, and what the dev `transformIndexHtml` in `vite.config.js` uses) merges the config file over the environment, and `ensureSiteInstalled({ seed })` adopts an environment-derived config, writes `data/react-wp-config.json` when the host can write (EROFS is tolerated), and re-asserts the `installed` option. Three properties are load-bearing: **no driver imports** (`pg`, `better-sqlite3`, `@libsql/client` must not enter a serverless bundle, so the DDL-capable caller injects a `seed` callback and a `skipped`/`failed` seed still leaves the site `installed: true`, because the verdict follows the config, not the write), **memoised and never throwing** (each engine calls it at boot or before its first refusal), and **`configIsConfigured` is a deliberate twin of `isConfigured` in `src/lib/runtime.ts`** — if you change one, change the other. Callers: `server.mjs` (before `configureSecuritySettings`), `getRuntimeConfig()` in `src/server/config.ts` (so the Hono/Vercel engines self-heal), `src/server/routes/plugins.ts` before its 409, and `src/server/adapters/node.ts` ahead of `runStartupMigrations()`.
- **The `window.__REACT_WP_CONFIG__` marker has two shapes, and both must be replaced.** `index.html` ships the literal `window.__REACT_WP_CONFIG__=null;`, but a build that resolved a config (`vite.config.js` now does) bakes a real object into `dist/index.html`, so `renderIndex` in `server.mjs` replaces the `=null;` literal when it is there and falls back to `/window\.__REACT_WP_CONFIG__=[^;]*;/` when it is not — the config the running process reads is the one that must win, which is how Step 5 → Dashboard works with no rebuild. `src/server/adapters/node.ts` replaces both shapes the same way; if you change one, change the other.
- **Supabase errors are plain objects, not `Error`s.** Use `describeDbError` from `src/lib/db.ts`; `instanceof Error` checks swallow them.
- **PostgREST embeds need a real FK to the embedded table.** `comments.author_id` references `profiles`, not `auth.users`, for this reason.
- **`server.mjs` loads `.env.local` itself** via `server/env.mjs`, which must stay the first import (ESM hoists imports, and other modules read `process.env` at load time). The only variables it needs are infrastructure: the database, the signing secret and the Supabase pair. Service credentials are **not** here — see the Integrations hub below.
- **No integration credential is read from the environment.** GitHub, AI, media storage and email are configured on **Settings → Integrations** (`src/components/settings/IntegrationsHub.tsx`) and stored in `system_settings`: `github_config`, `ai_config`, `media_storage_config`, `email_config`. Keys and shapes are declared once per side — `src/lib/integrations.ts` for the browser, `server/integrationConfig.mjs` (+ its `.d.mts`) for the server — and the *logic* exists once: `server/integrationConfig.mjs` (normalising, presence-only status, the two provider probes) and `server/integrationSettings.mjs` (`readIntegrationRows`, `readMediaStorageSettings`, `authorizeSettingsManager`), which `server.mjs`, `src/server/integrations.ts` and the `api/*` functions all import. `server/integrationsRoutes.mjs` owns the five routes and `ownsIntegrationPath` is the single list of them. Two things to keep in mind when touching this: `system_settings` is RLS-protected, so the server reads it through a direct connection (`DATABASE_URL`/`SUPABASE_DB_URL`), the service key, or an injected adapter — and `credentials.readable: false` in `GET /api/integrations/status` is the answer the hub shows a banner for, never a reason to fall back to `process.env`. The two POST test routes are the only ones that spend a credential, so they are the only ones that authorize the caller.
- **Integrations cards are a plugin registry too** (`src/core/integrations.ts`): `registerIntegrationCard` / `useIntegrationsRegistry()`, exposed as `integrations.registerCard` on the plugin context and through `src/lib/plugin-api.ts`. A card owns its own `system_settings` row and receives `{ status, refresh }`; `describe()` is what supplies the Configured pill.
- **SEO tags are written twice on purpose:** server-side in `server/seo.mjs` (what social crawlers read) and client-side in `src/lib/seo.ts`. This does not work on Vercel.
- **Content renders through `ContentRenderer`**, which portals shortcode components (e.g. `[rwp_login]`) into the sanitized HTML. Don't go back to raw `dangerouslySetInnerHTML` — not even inside it: it writes the HTML itself in a layout effect and finds the shortcode hosts in the same step. With `dangerouslySetInnerHTML` the hosts it had found were later replaced, every portal rendered into a detached element, and shortcodes showed nothing, with no error.
- **Account pages use the builder's Account Form widget** (`render/widgets/account.tsx`, screen = login/register/lost_password/profile/dashboard) when the builder is active: `withSiteDefaults` gives new ones that layout, and `upgradeAccountPages` converts chosen pages that still hold only their default `<p>[shortcode]</p>`. They keep the shortcode as classic content, so they still work with the builder off.
- **The TipTap editor (`ClassicEditor.tsx`)** syncs external values by comparing against the last HTML it emitted, because TipTap normalises HTML. Don't wrap it in a `<label>`: labels forward clicks to the toolbar `<select>`. Its CSS is scoped under `.editor` so parent form styles can't override it.
- Cloudinary uploads are unsigned (no secret needed); deletes are signed and go through `/api/media-delete`.
- **Plugins can own public routes, header items and server routes** (`routes.register`, `header.register`, `plugins/<id>/server.mjs`). Server modules must be imported by literal path in `server/plugins.mjs`, or Vercel won't bundle them; those imports sit between `rwp:server-plugin-imports` markers that the uploader and Delete rewrite (`server/serverPluginImports.mjs`), so keep one plain `import('../plugins/<folder>/server.mjs'),` per line there.
- **Uploading a plugin is a folder move, and on Windows that move must not be a bare `rename`.** `server/pluginInstaller.mjs` unpacks into `.rwp-tmp/` and then `moveIntoPlace` clears `plugins/<id>/` first (a `rename` onto an existing directory fails on Windows whatever its contents are — safe there and only there, because `assertNoCollision` has already answered 409 for a real plugin at that id), retries the rename while a handle is held anywhere in the tree (`EPERM`/`EACCES`/`EBUSY`/`EMFILE`: antivirus, the Vite watcher, an editor — measured here, where one child file open `FileShare.None` makes the folder `rename` answer EPERM *and* `cp` answer EBUSY), and falls back to recursive `cp` + `rm` when a rename cannot work at all (`EXDEV` across a mount or volume, a destination that stays in the way). A copy is not atomic, so a failed copy deletes what it wrote: the promise in the module header is that a failed install leaves nothing half-written for the build to find. `moveIntoPlace` is exported (and declared in `pluginInstaller.d.mts`) so a second stager never re-derives this.
- **`src/lib/db.ts` is a plugin-facing API, so its retired names stay as aliases.** The universal-client refactor (`939e730`, 2026-10-04) dropped `getSupabaseClient`/`tryGetSupabaseClient`, and bundled plugins import them anyway — `plugins/rwp-page-builder` alone did so in fifteen files. A plugin importing a name core no longer exports is not a soft failure: Vite answers `SyntaxError: The requested module '/src/lib/db.ts' does not provide an export named '…'` when that module is evaluated, and since `src/main.jsx` globs every plugin entry under `plugins/` eagerly, the throw happens before React mounts and blanks the whole site — public and admin, empty `#root`, nothing in the console but that one line. Production does not even get that far: `vite build` stops with `MISSING_EXPORT`. `plugins/` is untracked in git, so nothing in this repo compiles a plugin on its own — run `npm run build` after changing any export a plugin imports. `getSupabaseClient()` is an alias for `client` (a lazy client that throws when the CMS is unconfigured) and `tryGetSupabaseClient()` is `tryGetClient` (null instead); remove either only together with every plugin that imports it.
- **Shop (`plugins/rwp-shop`) prices, tax, shipping, coupons and stock are computed in SQL** (`shop_calculate`, `shop_place_order`). Never trust an amount from the browser. `shop_mark_order_paid`, `shop_claim_order_email` and `shop_set_gateway_data` are granted to `service_role` only; the server calls them with `SUPABASE_SECRET_KEY` after verifying the payment with the gateway.
- **Page builder (`plugins/rwp-page-builder`)**: the layout JSON lives in `pages.builder_data`, which anyone can read for a published page. So form email recipients are edited as `settings.private_*` on the widget but stripped on save into `builder_form_settings` (`stripPrivate` in `lib/api.ts`); keep that when adding private widget settings. Custom HTML is admin-only via the `builder_guard_html` trigger, not the UI. Widget styles are generated from JSON by `render/generateCss.ts` and target global `rwpb-*` classes in `render/builder.css`, so those class names must stay unhashed (not CSS modules). The editor canvas renders the real widget views; editor-only behaviour is injected through `EditorBridge` in `render/context.tsx`, so the public bundle never imports editor code.
- **Builder SEO tab** (`editor/seo/`) audits the live canvas DOM, not the JSON, so it sees real widget output. Editor-only UI must carry `data-rwpb-chrome` or it is audited as page content; the canvas root is `[data-rwpb-canvas-root]`. SEO fields live in the editor store (`seo`/`savedSeo`, part of `isDirty`). They are saved with the layout via `seoPayload`, which only sends columns the loaded row has. Checks that cannot be measured in the editor (backlinks, authority, dwell time) are "check outside the editor" notes, never guessed scores. Manual task ticks (keyword research, backlink outreach) are stored as booleans in `doc.settings.seoChecklist`, which is public for published pages, and are unscored (`scored: false`). Click depth (`siteSignals.ts`) walks home page → menus/header/footer → published page links.
- **AI Section Refine** (Gemini): the key is server-only and lives in the `ai_config` row written by Settings → Integrations (an OpenAI key and model are the alternative; see the Integrations convention above), called from `plugins/rwp-page-builder/serverAi.mjs` (route `POST ai/section`, edit_posts, 8 calls/user/min). Never use a `VITE_` key: Vite compiles those into public JS. The browser sends only extracted copy (`services/geminiSectionOpt.ts`: text/textarea/richtext settings, skipping URLs, ids, `private_*`, admin-only widgets), and only replacement strings come back. The server rejects any rewrite that changes `{{tags}}` or shortcodes. `applySectionCopy` patches them in one undo step and skips fields edited since the request.
- **Builder widget pack**: shared building blocks (carousel, gallery lightbox, `TemplateContent`, `PostScope`, taxonomy filter bus, `useAsync`) are in `render/widgets/kit.tsx`; reuse them rather than writing another carousel. Visitors read templates only through `builder_template_public()` (published-page usage check), so any widget showing a template must go through `TemplateContent`. Carousel and Posts Slider read responsive counts back from CSS variables (`--rwpb-per-view`, `--rwpb-columns`), so keep those names. Shop widgets are registered by the shop plugin (`plugins/rwp-shop/builder`), and `registerWidget` returns a cleanup; the widget panel re-renders through `subscribeWidgets`. The dynamic tag popover is portalled into `[data-rwpb-shell]` with fixed positioning; rendering it inside the sidebar gets it clipped.
- **Site templates (Page Builder → Templates)** are `pages` rows with `is_site_template` + `template_type` (one row per type; types and default layouts in `plugins/rwp-page-builder/lib/siteTemplates.ts`, allowed values in SQL `rwp_template_types()`). Core never imports the builder: it renders `<SiteTemplate types=[…] fallback=…>` (`src/components/SiteTemplate.tsx`) for the header/footer (`PublicLayout`), single post/page/404 (`PublicContent`) and search/archives (`PublicArchive`, routes `/search`, `/category/:slug`, `/author/:id`, `/date/:y[/:m]`), and the builder registers `content.registerTemplateProvider`. Live templates are preloaded in one query before the first public render (`preloadSiteTemplates` in `App.tsx`) so nothing flashes; `has()` must stay synchronous. A page's own builder layout beats the Single Post/Page template; `archive_<kind>` beats the shared `archive`. Template rows are never shown at their own slug. Shop routes use the same rows through `withShopLayout` (`plugins/rwp-shop/builder/ShopLayoutRoute.tsx`) and widgets read the product/category/account sub-page from `useShopRoute()`; archive widgets read `useTemplateContext()`. Only `manage_shop` (Administrator, Shop Manager) may create or edit templates (`builder_guard_site_template` trigger).
- **Default content is installed once per group** by `rwp_install_default_content` ('site' and 'account' from core, see above; 'shop': the six shop templates, from the builder's `rwp_admin_ready` action). The `rwp_default_content` option records installed groups, so deleted defaults are not recreated.
- **Header and footer rows use zones** (`RowBlocks` in `ThemeLayoutRenderer.tsx`): once any block in the row has an explicit alignment, blocks are grouped into `.rwpt-zone-start/center/end`; "Auto" (`inherit`) follows the previous block, and Left/Right stay physical in RTL. Rows where every block is `inherit` render the old way. Don't go back to `margin-left: auto` per block: two right-aligned blocks split the free space. The zone rule is `rowZones` in `src/lib/theme.ts`, shared with the Theme Editor, which draws row containers as Left/Center/Right lanes (`VisualBuilder.tsx`): a drop into a lane is `moveBlock` with `align`, one undo step, and each card has ⇤ ◎ ⇥ buttons.
- **`?preview=1` on a public page** loads it without the published filter (the editor's "Preview page" for drafts); RLS still limits drafts to their author and `edit_others_posts`.
- **The header layer is z-index 9800** (`.rwp-header` in `theme.css`, `.rwpb-template-header` in `builder.css`): above every page section, below the full-screen overlays (off-canvas 9990, search overlay 9995, lightbox 10000). New overlays that must cover the header go above 9800; nothing in page content should.
- **Public search boxes are `LiveSearch`** (`src/components/LiveSearch.tsx`, global `rwp-live-search*` classes): Go opens `/search?s=`, published pages/posts matching the title are listed as you type. Theme Search block, Search widget, archives and the builder's WordPress Search widget use it.
- **Per-page `show_header` / `show_footer`** (20261002) are sent by `PageEditor` only when the loaded row has them or one is switched off, so saving works before the columns exist.
- **The Theme Header/Footer widgets** wrap the Theme Editor output in `.rwpb-theme-part`, which the base `.rwpb-root` heading/paragraph resets skip via `:where(:not(.rwpb-theme-part *))`. Keep that, or the default header template stops matching the theme header.
- **Content renderers and actions** (`content.registerRenderer` / `registerAction` in `src/lib/rwp.tsx`) let a plugin replace a page's public body and add links to Pages & Posts.
- **There is one hook registry: `src/core/hooks.ts`.** `rwp.actions` / `rwp.filters` are thin wrappers over it, so both APIs see the same callbacks — never add a second registry. Filters must return the value; one returning `undefined` or throwing is logged and skipped so a broken plugin cannot blank a page. `<HookSlot name="…">` (`src/core/HookSlot.tsx`) is a filter over a `{id, node}[]`, which is why `addSlotContent` and a plain `addFilter` on the same name compose. Slots re-render on registry changes via `subscribeHooks`, so plugins activating after first paint still appear.
- **`the_content` is filtered before sanitizing, never after** (`ContentRenderer`), or a filter could inject a `<script>` into every page. Chrome that happens to be HTML (Theme Editor custom HTML, area code) passes `applyContentFilters={false}` so a content filter does not also rewrite the header.
- **Language settings are four rows in `options`** (`default_site_language`, `default_admin_language`, `show_header_language_switcher`, `supported_languages`), not keys in `rwp_app_settings`, because the public site reads them before anything else loads. `src/lib/i18n.ts` applies `lang`/`dir`/`--rwp-font-family` to `<html>` at import time from `localStorage` and again after `initI18n()`, which `App.tsx` awaits **before the first render** — move it later and every RTL site flashes LTR. `t()` falls back active locale → site default → English → the passed fallback → the key; showing the key is deliberate, it is a readable bug report.
- **Per-language builder layouts**: `pages.builder_data` stays the layout for the row's own `locale`; other languages live in `pages.builder_data_i18n` keyed by locale. `saveBuilderPage` only names `builder_data_i18n` when the loaded row has the column, or PostgREST rejects the whole update on a database without those columns. Translated layouts are cloned with the **same node ids** on purpose, so all languages of a form share one `builder_form_settings` row. In the editor, `doc` is the language being edited and `otherDocs` the rest; `isDirty` compares every locale (`layoutsDirty`), and undo history is cleared on a language switch because a stack mixing two layouts would undo invisible edits.
- **Logical CSS properties are the convention** (`inset-inline-start`, `padding-inline-start`, `text-align: start`), so `dir="rtl"` mirrors the site without an RTL stylesheet. Sides that are the designer's explicit choice keep physical properties: `.rwpb-icon-box-left`, `.rwpb-ribbon-right`, `.rwpb-offcanvas-left`, `.rwpb-tooltip-right`, `.rwpb-author-right`, and anything centred with `left: 50%` + `translateX(-50%)`.
- **Settings → Translations (`rwp_translations`, `src/lib/translations.ts`) is a data source for the one `translate()`, not a second i18n system.** Database strings live in their own map in `i18n.ts` (`setDatabaseTranslations`) and beat bundled/plugin strings per locale, whatever loads first. They are awaited in `App.tsx` after `initI18n()` (`initDatabaseTranslations`), or edited wording flashes in after the bundled one. Unique key is `(translation_key, locale)`. A null `translation_value` is a discovered, untranslated key and is **never applied**. `rwp_report_missing_translations` is deliberately executable by anon and bounds itself (option check, supported locales, 50/call, 2000 untranslated rows cap); the browser only reports a locale after its strings loaded (`applied`), or every key looks missing mid-switch. A failed load keeps the locale in `requested`: retrying from the `subscribeLocale` listener would loop, because applying the cached copy notifies it.
- **Persian Origins (`plugins/persian-origins`) has no language state of its own**: it follows core's locale and mirrors it into `po-*` body classes. Translated titles/excerpts/bodies render every language at once and CSS hides the inactive one, because `PublicContent`/`PublicHome` don't re-render on a language switch. Its `rwp_post_title`/`rwp_post_excerpt` filters return a React component (priority 100, after string filters), so keep those filters' results rendered as JSX children. The body goes `rwp_page_content` (adds `<!--po-page:id-->`) → `the_content` (priority 1, expands it), refreshed by `refreshFilters()` in `src/core/hooks.ts`. Page translations are a plugin table, not `pages` columns, because the uninstall backup exports only declared tables. Category text is core translation keys, not plugin data.
- **Persian Origins' Site text translates the rendered public DOM** (`plugins/persian-origins/lib/pageTranslator.ts`): text nodes and attributes are rewritten in place from a WeakMap of originals, matched by `phrase.<cyrb53 of the normalised text>` keys in `rwp_translations`. Never replace or wrap a text node there (React holds references to them); never translate inside `[data-rwp-user-content]` (put it on anything a visitor wrote) or `.po-text`. It reads with `lookupTranslation` (`src/lib/i18n.ts`), not `t()`, so thousands of lookups cause no fallbacks and no missing-key reports. Renaming an English UI string silently orphans its bundled Farsi in `lib/phrases.fa.ts`; the new wording then shows up under Site text as untranslated.
- **The header language switcher is opt-out, not opt-in** (`block.settings.show_language_switcher !== false` in `HeaderActions`): layouts saved before it existed have no such key, and treating that as "off" would silently remove it from every site with a saved theme.
- **App Settings (`src/lib/appSettings.ts`) are one JSON document in the public `rwp_app_settings` option**, read in SQL by `rwp_app_settings()`. Media scoping in it is applied by `rwp_can_manage_media()`; upload limits by the `media_enforce_upload_rules` trigger. Rename a key and all of those break silently. Anything private (quota overrides, keyed by email) goes in its own table, never that option.
- **`media_enforce_upload_rules` overwrites `uploaded_by`, `bytes`, `width` and `height`** (pinned on insert, frozen on update) for any caller with `auth.uid()`. Don't write code that expects to change them from the browser.
- **Media folders** are `media.folder` paths (`general`, `blog/2026`; format enforced by `media_folder_format`) plus `public.media_folders` rows so empty folders exist. The `media_record_folder` trigger adds rows for any folder media is put in. Rename/delete go through `rwp_rename_media_folder` / `rwp_delete_media_folder`, which are SECURITY INVOKER and all-or-nothing, so media RLS still decides. Moving media only changes the library row, never the provider file: in Cloudinary's fixed folder mode that would change the URL. Pages/posts and shop products also have a `trash` status; public reads already require published/publish.
- **`/api/media-delete` takes only the media row `id`** and reads the provider id from the database. Never go back to trusting a provider id from the request body.
- **Tracking scripts are injected twice on purpose, but only run once**: `server/seo.mjs` writes them plus `<meta name="rwp-scripts">`, and `injectTrackingScripts` skips when that marker exists. Both use `src/lib/scriptSanitizer.js`, plain JS so Node can import it.
- **New `public` functions are executable by anon by default** (Supabase default privileges). Internal SECURITY DEFINER helpers must `revoke execute ... from public, anon, authenticated`.
- **Admin navigation is data** (`src/lib/adminNavigation.ts`): core items, plugin pages (inserted after Comments) and their `submenu`s, filtered by capability. Screens take the selected submenu id as a prop (`tab`/`view`/`subsection`) instead of keeping their own tab state; the location lives in `/admin?section=…&tab=…`. Renamed ids go in `legacySections` so old links keep working.
- **Dashboard → Overview's checklist** is `src/lib/setupChecks.ts` plus each plugin's `admin.registerSetupCheck`. Checks report whether a server secret is set, never its value.
- **Plugin schema install, uninstall and the site reset need a direct Postgres connection**, resolved by `server/db.mjs`: `SUPABASE_DB_URL` from `.env.local` first, then `DATABASE_URL` — the name the Setup Wizard's own `.env` block writes, so reading only `SUPABASE_DB_URL` is what made a wizard-installed site ask for a password it had already been given — otherwise a password sent with the request (the Setup Wizard's long-standing fallback). All three are **`server.mjs`-only** — they run DDL, delete folders and rewrite `data/react-wp-config.json`, none of which a static host can do. The browser distinguishes "this host has no such endpoint" (`EndpointUnavailableError` in `src/lib/pluginSchema.ts`) from a real SQL failure, because activation must still work on Vercel while a bad `schema.sql` must not be swallowed.
- **Provider folders are namespaced and are not `media.folder`** (`src/lib/mediaScope.js`, plain JS so `server.mjs` can import it). Library uploads go to `media/<library folder>`, a plugin's to `plugins/<id>/…`. `media.folder` is the *library* folder shown in the admin and changes when an item is moved; the provider folder is fixed at upload time and is what public ids are built from. Cloudinary cleanup keys off the public id and the URL, never `media.folder`. A plugin may narrow its prefix in `manifest.json` (`media.prefixes`) but `readMediaPrefixes` refuses anything outside its own `plugins/<id>/` — that check is the only thing stopping an uploaded manifest from claiming `media` and wiping the library.
- **Cloudinary bulk deletion is `server/cloudinary.mjs`**, hand-rolled against the Admin REST API (Basic auth, no signature) because there is no `cloudinary` npm package here. Nothing in it throws: a missing asset, a revoked key or an outage becomes a warning so the database cleanup still runs. It deletes both by prefix (catches files the `media` table forgot) and by recorded public id (catches dynamic-folder clouds, where the folder never appears in the public id). **An empty prefix is refused** — Cloudinary reads it as "the whole cloud", which on a shared account destroys other sites. Site reset therefore deletes recorded ids plus `media/` and `plugins/`, never `all=true`.
- **ImageKit files are not bulk-deleted.** Its delete API needs the stored fileId and has no prefix or bulk operation, so a reset reports the count instead of making one request per file.
- **Uninstalling a plugin is three decisions, not one** (`PluginUninstallModal`): does the code go, does the data go, is there a backup first. The order in `server/adminRoutes.mjs` is fixed — export, then drop, then remove the folder — so nobody ends up with wiped tables and no backup file. Wiping requires typing `DELETE`, checked on the server too.
- **Settings → Advanced → Reset Website** drops the `public` schema, deletes every `auth.users` row and flips `installed: false`. Gated on `profiles.role` being administrator/super_admin (deliberately *not* `manage_options`, which App Settings can grant), on re-verifying the caller's own password against Supabase Auth, and on typing `RESET`. It does **not** delete Cloudinary/ImageKit files; it reports how many there were.
- **Dashboard → Updates only checks; it never installs.** Versions come from `package.json` and plugin manifests, compared against `updates.json` (fetched from GitHub by default). Bump both when releasing, and note any schema change there.
- **The public header, footer, sidebar, comments and home page render from the Theme Editor layout** (`theme_settings.layout_structure`, `src/lib/theme.ts`, `src/components/theme/ThemeLayoutRenderer.tsx`). The default layout must keep reproducing the pre-editor look, because sites that never saved a theme get it. Anything read from the layout goes through `normalizeLayout`, and every block renders inside `BlockFrame`, which has its own error boundary. The `rwp-*`/`rwpt-*` class names are what Custom CSS targets, so keep them global and stable. Theme CSS and scripts are written twice, like tracking scripts: `server/seo.mjs` adds them with `<meta name="rwp-theme">`, and `applyThemeDocument` skips scripts when that marker is present. `themeStylesheet` and the server both concatenate `custom_css` + `custom_comments_css`.
- **Engagement (20261004)**: likes, bookmarks and page_views key items by `(target_type, target_id text)`, with no foreign key, because pages have bigint ids and products uuid ids. Core only knows `page`; other types plug in through `rwp_engagement_target_<type>(text) returns jsonb` (null = not public) and `rwp_engagement_feed_<type>(uuid, int, timestamptz)`, found by name at run time, so core never references a plugin object. The shop defines both for `product`, and its triggers on core's `likes`/`page_views` are created only when those tables exist (so the shop still activates without the core engagement tables). `pages.views_count`/`likes_count` (and the shop's) change only inside the counter triggers: the guard triggers let a write through only at `pg_trigger_depth() > 1` or without `auth.uid()`, so views are recorded by inserting into `page_views`, never by updating `pages` from a function. The browser sends the state it wants (`rwp_set_like(..., p_liked)`), never a toggle. `rwp_record_view` is anon-callable and bounds itself (30-minute dedupe, per-hash hourly caps, `engagement.track_views`); it stores only md5 hashes salted by `rwp_view_salts`, rotated daily. Never store a raw IP, user id or visitor token there.
- **Engagement UI** (`src/lib/engagement.ts`): one store batches every button's state into one `rwp_engagement_state` / `rwp_follow_state` call per tick; components render nothing for `null` (not public, feature off, tables missing). Visibility is `engagementVisible(settings.engagement, feature, { placement })`: `placement: 'auto'` (places the site adds buttons itself) also checks the granular toggles, `'manual'` (shortcodes, widgets) only the global ones. `PublicContent` provides `EngagementTargetProvider`, which is how `[rwp_like]` without an id finds its post (portals keep context).
- **Shop commerce tools (20261005)**: an accepted offer becomes a single-use `fixed_product` coupon (product-, email- and one-unit-bound) created by `shop_offer_coupon`, so the agreed price is enforced by `shop_calculate`; never add a "price override" path from the browser. Bundle discounts are applied inside `shop_calculate` by `shop_apply_bundle_discounts`. Q&A publishing and asker fields are enforced by triggers. The offer and price-alert emails (`offers/notify`, `price-alerts/send`) run with the manager's own session through RLS, not the secret key.
- **Shop backup (Shop → Backup, 20261006)** is `shop_backup_export` / `shop_backup_import(p_backup, p_modes, p_dry_run)` in `plugins/rwp-shop/schema.sql`, with the UI in `admin/BackupAdmin.tsx` + `lib/backup.ts`. Each table's "same item" rule is a SQL condition between existing `x` and incoming `r` passed to `shop_backup_put`, and every reference is declared in its `p_refs` (`"table"`, `"[]table"`, `"{}table"`, `"[field]table"`, `"@user"`). A new shop table or a new column pointing at another row needs an entry there, or imports into another site keep ids that don't exist. `shop_backup_put`/`_resolve`/`_remap`/`_fix`/`_links`/`_prune` run dynamic SQL from their arguments, so they must stay revoked from everyone. The preview is the real import rolled back (errcode `RWPDR`), so nothing in the import may have non-transactional side effects: no `nextval`/`setval` in a dry run (guarded by `rwp_shop.backup_dry_run`), no emails, no HTTP.
- **Chat (`plugins/rwp-chat`) gives anon no table access at all.** RLS refuses anonymous visitors even a `select` on `chat_sessions` — a readable row is a list of every lead's email and phone. They reach their own conversation only through `rwp_chat_start/post/history/identify/request_agent/close`, each of which re-checks `chat_sessions.session_token` (48 hex characters, regenerated by the `chat_sessions_touch` trigger on insert so a caller can never choose it). Staff use ordinary queries: `moderate_comments` reads and replies, `manage_options` deletes transcripts. **Credentials are `chat_secrets`, never `options`** — options is world-readable, so a bot token there would be downloadable by every visitor; the table has RLS on and *no policy*, so only the server's secret key reaches it, and the admin screen goes through `rwp_chat_save_secrets` / `rwp_chat_secrets_status` (which reports set/not set, never a value). The public `chat_whatsapp_number` option is the exception and is public on purpose: it ends up in a `wa.me` link the visitor clicks.
- **Chat never references a shop object.** It publishes `rwp_chat_card_<type>(text)` and `rwp_chat_order_status(text, text)` and finds them with `to_regprocedure` at run time, like core's `rwp_engagement_target_<type>`; `rwp_chat_card` falls back to `rwp_engagement_target`. The shop implements both (end of `plugins/rwp-shop/schema.sql`, dropped by its `uninstall.sql`). `rwp_chat_card_product` accepts a slug **or** a uuid, because the page announces itself before it knows the id. Order lookup needs the order key *and* the email on the order: a key alone is in confirmation emails and browser history. Which page a chat is about is announced with `doAction('rwp_chat_subject', type, id)` and in-chat add-to-cart with `doAction('rwp_chat_add_to_cart', id, qty)` — the one registry, so neither plugin imports the other.
- **Gemini in the chat is server-only and reads the transcript itself** (`plugins/rwp-chat/serverAi.mjs`, route `POST ai/reply`, 10 calls per session per minute; the database separately caps a session at 20 messages a minute). The browser sends only `{session_id, token}`; the server loads the messages with the secret key, calls Gemini and writes the reply as a `chat_messages` row with the model on it. That is what stops a visitor forging what the bot "said" and what makes the AI audit in Chat → Inbox real. `GEMINI_API_KEY` only — a `VITE_` key is compiled into public JS.
- **Chat attachments are recorded by the server, not the browser** (`POST attachments/record`). `public.media` only accepts inserts from someone with `upload_files` and most visitors are anonymous, so the browser uploads to Cloudinary and the server writes the media row with the secret key (`uploaded_by` stays null, which is correct). Provider folder `plugins/rwp-chat/chat_media` (what an uninstall deletes by); library folder `chat_media`.
- **`chat_media` is a "quiet" media folder** (`quietMediaFolders` in `src/lib/mediaFolders.ts`): the Media Library leaves it out of "All media" and its count, and shows it only when the folder itself is opened, so a support inbox full of screenshots does not bury the site's own images. It is otherwise an ordinary folder. Add another by putting it in that list — `MediaManager` and `FolderSidebar` read it, nothing else.
- **Private per-user data goes in `profile_details`, not `profiles`** (every signed-in user can read `profiles`). Its policies allow the owner, `list_users` to read and `edit_users` to write.
- There is no local database, but SQL can be exercised in PGlite (`@electric-sql/pglite` with the `pgcrypto` contrib) with small stubs for `auth.uid()` and the anon/authenticated/service_role roles.

- **The security engine is `server/middleware/` plus `server/securityRoutes.mjs` and `server/sitemap.mjs`** (Settings → Security; `src/lib/security.ts`, `src/lib/antiBot.ts`, `src/lib/session.ts`, `src/components/settings/SecurityPanel.tsx`). Its knobs are **one `options` row each** (seeded by `schema.sql`), because `server.mjs` reads them with the publishable key on a 30-second timer and never per request; `securitySnapshot()` is **synchronous** and refreshes in the background, so middleware never awaits its own configuration. The **CAPTCHA secret is not an option row** — `options` is world-readable — it lives in `rwp_security_secrets` (RLS on, no policy), written through `rwp_security_save_secrets` / `rwp_security_secrets_status`, or overridden by `ANTI_BOT_SECRET_KEY`. Rate-limit counters, bot flags and cached pages are **per-process memory, never tables**: a limiter that writes a row per request is the latency it exists to remove, and a flag a bot can make you persist is a write primitive. `X-Forwarded-For` is trusted only when `TRUST_PROXY=true`, or an attacker picks their own rate-limit bucket.
- **Auth is browser → Supabase, so the anti-bot check on login/register/comments runs *before* the request, not around it.** It stops bots driving a real page; Supabase's own auth limits, email confirmation and the comment RLS policies stop the rest. Forms that do reach `server.mjs` exchange a solved challenge for a clearance ticket (`POST /api/security/verify`) which `requireClearance()` verifies — those cannot be bypassed. Say which of the two a given form is; claiming otherwise is how the real protections get removed later.
- **The page cache holds the finished HTML** (index.html after `server/seo.mjs`), keyed by path, and refuses any request with an `Authorization` header **or any cookie** — that is what stops one person's page being served to another, and why `signOutAndRedirect` clears the session cookie. `/admin`, `/builder/*` and any unknown query string bypass it. Purge is explicit (`purgePageCacheQuietly` after content and settings saves); the TTL is only the backstop. Vite fingerprints are **base64url**, not hex — the `immutable` rule in `assetCacheHeaders` must match `-[A-Za-z0-9_-]{8,}`.
- **`rwp_backup_export` / `rwp_backup_import` skip `profiles`, `rwp_security_secrets` and `chat_secrets`.** Backup files get downloaded and emailed, so a credential inside one leaks for a long time; a restore leaves those tables alone for the same reason. Both functions live in `supabase/schema.sql`, and the two exclusion lists must stay identical.
- **Response compression (`server/middleware/compression.mjs`, 20261011) is deliberately independent of `cache_enabled`.** It is a pure transport optimisation with none of the page cache's privacy/staleness trade-offs, so unlike the page cache it defaults **on** (`cache_enable_compression`). Only text-ish content types compress (`compressibleContentType`) — never images/fonts/video, which are already compressed and would just burn CPU to get bigger. Two different cost models, on purpose: a **page cache entry** is compressed exactly once, at store time in `pageCacheStore` (a MISS or a background stale re-render), so every HIT after that is zero compression CPU — that split is the entire point of caching output rather than a per-request gzip middleware. A **built asset** under `dist/` is compressed once per process, the first time it's requested, and kept forever in `assetCompressionCache` (unbounded is safe: Vite fingerprints every asset by content hash, so a pathname never means different bytes within one process's life, and a redeploy restarts the process). `compressForResponse` is the one entry point that never leaves a dangling `Content-Encoding` header when the body was too small to bother (`MIN_COMPRESS_BYTES`) — use it, not `compressSync` directly, at any new response site. `json()` in `server.mjs` takes `request` as its first argument for exactly this negotiation; every call site is inside the same request-handler closure, so `request` is always in scope.
- **`cache_auto_purge_on_save` only gates *automatic* purges.** `purgePageCacheQuietly` (called after every page/settings save) sends `reason: 'auto'`; the admin's own "Purge the whole page cache" button sends `reason: 'manual'` and always runs regardless of the toggle — turning auto-purge off must never disable the one button that exists to override it.
- **`/sitemap.xml` and `/robots.txt` are server routes ahead of the SPA fallback.** The sitemap is read with the **publishable** key on purpose, so it can only contain what a visitor can already see. An empty `robots_txt_content` means "serve the generated default", never "serve an empty file".

## Working with the owner

Changes are tested by hand in the browser against the live Supabase project, and the exact error text gets reported back. Error messages must name the real cause: a wrong diagnosis in an error string costs a debugging round.
